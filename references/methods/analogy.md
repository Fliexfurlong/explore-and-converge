# Structural analogy: transfer a mechanism that addresses the bottleneck

Use when conventions in one domain limit directions or candidates merely rename existing solutions. This method supplies ways to reframe a problem; distant domains are not guaranteed to help. Begin with a small set suited to the current question, without domain quotas.

## 1. State the problem as a structure

Extract from current facts: who participates, what flows, where it fails, and what the user wants to change. Temporarily remove product names and solution terms while retaining conditions that determine the bottleneck.

Consider a hypothetical shared tool room: tools return on time, but nobody knows which are damaged. A structural statement is: "Items circulate among people, but handoffs transfer the item without its usable status." "We need a smarter tool-management app" is still a solution rather than a structural description.

The statement is a hypothesis to check. If the point of failure is unclear, retain competing explanations and verify the most consequential one if needed. Do not reshape the real problem into a convenient analogy story.

## 2. Find sources with similar structure and different solution logic

First ask which systems deal with the same failure, then choose sources. Distance cannot be established merely by an unfamiliar name; related industries may use different mechanisms. Start with a few sources whose mechanisms differ meaningfully. Stop or change axes when they repeat.

These questions are search prompts, not verified universal rules:

| Target bottleneck | Systems to consider | Possible mechanism to extract |
|---|---|---|
| State or responsibility is lost at handoff | Relays, shift handovers, item circulation | Does the transferred unit include state, next action, and receipt confirmation? |
| Arrival rate and processing capacity mismatch | Appointments, buffers, production scheduling | Change arrival rhythm, batch size, work in progress, or queue rules. |
| Resources exist but are hard to discover and match | Indexes, catalogs, matching systems | Make demand or available resources visible and change discovery or pairing. |
| Coordination lacks a central controller | Rotation, local feedback, shared conventions | Let local signals or rules provide part of the coordination. |

Verify these mechanisms if presenting them as facts about real systems or evidence of effectiveness. Label hypothetical designs accordingly. Do not pick a supposed standard answer mechanically from the table.

## 3. Map before transferring

For each promising source, explain:

1. Which source actors, objects, and failures correspond to the target's.
2. How the source changes that failure rather than merely looking similar.
3. After transfer, who does what and when, and how information or resource flows change.
4. Which conditions the mechanism needs, whether the target has them, and what cannot be copied.

Do not start with a ready-made suggestion and decorate it with a metaphor. If no flow, incentive, order, responsibility, or feedback changes, a mechanism has not yet been transferred.

## 4. Check mismatches and reopen when needed

- **Surface resemblance:** shared words, style, or imagery without a mechanism. Identify the missing mechanism rather than adding decoration.
- **A decisive part has no counterpart:** a source may address congestion while the target lacks participation. Matching role names can still answer the wrong question.
- **Repeated role reuse or added rules:** check whether invented details are propping up the analogy. Abstraction and simplification are allowed, but decisive differences must remain.
- **Requires new resources or authority:** state whether the target has them. Preserve unknowns as conditional candidates rather than immediately actionable advice.

After repeated mismatches, revise the structural explanation. If no useful mapping emerges, explain the sticking point and switch methods or stop within the current authorization. No useful analogy is also a result. Report actual mismatches; do not manufacture failures for a template.

## 5. Extract results without converging too early

Keep promising directions whose mechanisms remain incomplete and identify gaps. Merge transfers sharing a mechanism and explain which default premise they jointly change. Do not force a shared discovery if there is none.

Deliver for the user's requested stage. For divergence, give directions, relevance, and open conditions. For selection, hand off to comparison and check complementarity, dependencies, and applicability before deciding whether ranking is appropriate. Novelty does not automatically outrank a conventional solution.

## Brief example: useful and superficial transfers

These are hypothetical teaching examples, not actual tests or evidence of real-world effectiveness.

- **Promising transfer:** borrow a handoff design with receipt confirmation. Tool returns include the last-use status and a receiver's confirmation. Someone must receive them; adding a form that nobody reads is insufficient.
- **Another mechanism:** separate physical return from restoration to a borrowable state. Unchecked tools enter a distinct state. This can reduce reborrowing of tools with unknown condition, at the cost of turnaround delay and inspection effort.
- **Surface analogy:** "The tool room is like an orchestra, so its interface should be more harmonious." This does not explain how condition information propagates and cannot support a direction for detecting damage.

The first two may complement each other or share the same handoff cost. Do not add their effects directly. These examples distinguish mechanisms from mismatches without restricting real exploration to the same answers.
